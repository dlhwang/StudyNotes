# Unit of Work 작업 가이드

여러 세션에 걸치는 작업을 **Unit of Work(작업 단위)** 로 나눠 문서로 진행하는 방식이다.
도구와 무관하게, 사람과 모든 에이전트가 같은 규칙을 따른다.

## 1. 전체 흐름

1. 작업을 여러 개의 Unit으로 쪼갠다. **하나의 Unit은 한 번의 작업 세션에서 끝낼 수 있는 크기**로 나누고, 크면 더 쪼갠다.
2. 전체 작업을 정리하는 개요 파일 `docs/<scope>/00-overview.md` 를 만든다.
   - 각 Unit을 체크박스(`- [ ]`) 목록으로 나열한다.
3. Unit마다 별도 파일 `docs/<scope>/units/unit-NN-<slug>.md` 를 만든다.
   - **그 파일 하나만 읽고 바로 착수할 수 있을 만큼** 자세히 쓴다.
   - Unit의 **Goal** 을 명확히 정의하고, Goal 도달을 완료 기준으로 삼는다.
4. 작업에 쓸 수 있는 가이드·스킬·명령이 있으면 확인하고 활용한다.

## 2. 개요 파일 구성 (`00-overview.md`)

```markdown
# [작업명] 작업 개요

## 목표
(전체 작업이 달성하려는 상태를 1~3문장으로)

## 계획 상태
- 작성일 / 기준 브랜치 / 선행 커밋

## 확인된 문제
(착수 근거가 된 사실. 측정값·재현 결과는 수치로)

## 설계 결정과 가정
| 결정 | 선택과 이유 | 비교한 대안 |

## Unit of Work 목록
- [ ] Unit 01: [제목] — `units/unit-01-xxx.md`
- [ ] Unit 02: [제목] — `units/unit-02-xxx.md`

## 의존관계
(`01 → 02`, 병렬 가능 여부)

## 진행 규칙
(아래 4장을 따르고, 작업별 추가 규칙이 있으면 적는다)

## 상태 기록
| Unit | 상태 | 검증 결과 |

## 전체 완료 기준
- (모든 Unit의 Goal이 합쳐져 달성되는 상태)
```

## 3. Unit 파일 구성 (`units/unit-NN-xxx.md`)

```markdown
# Unit NN: [제목]

## Goal (목표)
("~을 한다"가 아니라 "~된 상태가 된다". 완료 여부가 판정 가능하게)

## 배경 / 컨텍스트
(왜 필요한가, 전체에서 어떤 역할인가)

## 선행 조건 (Dependencies)
- 먼저 완료돼 있어야 하는 것 (선행 Unit, 파일, 데이터, 환경)
- 참고할 기존 파일 경로

## 작업 범위 (Scope)
### 한다
- 구체적으로 나열
### 하지 않는다
- 범위 밖을 명시해 스코프 크립을 막는다

## 상세 작업 단계
1. ...

## 사용할 수 있는 SKILL / 참고 자료
- 가이드 문서, 명령, 기존 구현 본보기

## 완료 조건 (Definition of Done)
- [ ] 조건 (명령·테스트로 검증 가능하게)
- [ ] Goal에서 정의한 상태 달성 확인

## 산출물 (Output)
- 생성·수정되는 파일 목록
```

## 4. 진행 규칙

- **자기완결성** — Unit 파일만 보고 작업할 수 있어야 한다. 다른 Unit이나 개요를 계속 참고해야 이해되게 쓰지 않는다. 필요한 경로·계약·검증 명령은 Unit 파일에 직접 적는다.
- **Goal 우선** — 모든 단계는 Goal을 위해 존재한다. Goal이 애매하면 Goal부터 구체화한다.
- **체크박스는 착수를 뜻한다** — Unit을 착수하는 즉시 개요의 체크박스를 `[x]` 로 바꾸고 Unit 상태를 `진행 중` 으로 둔다. **체크가 완료를 뜻하지 않는다.**
- **완료는 상태 기록 표에 남긴다** — 완료 조건을 검증한 뒤 개요의 상태 기록 표에 `완료` 와 검증 결과(실행한 테스트와 결과 수치)를 적는다. 차단·실패면 완료로 표시하지 않고 사유를 적는다.
- **착수 전 확인** — 선행 Unit의 산출물(코드·파일)이 실제로 있는지 확인하고 시작한다.
- **최소 diff** — 변경 전에 수정할 파일과 이유를 밝히고, 관련 파일만 읽고 고친다. 범위 밖 리팩터링은 하지 않는다.
- **순서** — 기본은 순서대로 착수한다. 의존관계가 없으면 병렬 진행할 수 있지만, 같은 파일을 고치면 순서대로 한다.

## 5. 이 리포에서의 규칙

- 한글 Markdown을 편집하기 전에 콘솔 코드 페이지와 출력 인코딩을 UTF-8로 맞춘다.
- 빌드·테스트는 Gradle Wrapper만 쓴다. Unit에서는 해당 테스트를, 마지막 Unit에서는 전체 테스트(`.\gradlew.bat test`)를 실행한다. 실패가 환경 문제인지 코드 문제인지 구분해 기록한다.
- 테스트는 실행 중인 개발 DB가 아니라 테스트 전용 H2(PostgreSQL 모드)를 쓴다.
- 공개 API·권한·트랜잭션·엔티티 구조가 바뀌면 범위를 다시 명시하고 `atworks-schema.sql`·`README.md`·관련 `docs/` 를 함께 갱신한다.
